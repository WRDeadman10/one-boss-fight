## M3 player combat (2026-10-18)

| Decision | Reason |
|---|---|
| All combat state lives in C++ components: `URPGAttributeComponent`, `URPGCombatComponent`, `URPGMeleeTraceComponent`, `URPGTargetLockComponent`; data in `URPGWeaponData` (Data Asset) | Testable headlessly; new weapons and bosses are data |
| Single damage path: `URPGCombatComponent::ProcessIncomingHit` | One place for i-frames, block, poise, stagger, death |
| Windows come from anim notify states (`RPGANS_HitWindow`, `ComboWindow`, `IFrames`, `CancelWindow`); without a montage the same windows run from fallback times | Animation owns timing like Souls games; combat is testable without animations |
| Melee trace sweeps each sample point from its previous to current position every frame, once per swing per target | Frame-rate independent hits; verified from 1 to 480 frames per crossing |
| Hit windows in the montages were placed from the sword tip speed (peak above 40 %), `Scripts/Editor/setup_m3_content.py` | First pass matches the visible swing; tune in the montage editor |
| Montages are built from Greystone sequences and play in slot `UpperBody` (the only slot in its AnimBP) | The factory default `DefaultSlot` does not exist there |
| Input: LMB light, RMB heavy, Space dodge, Q or MMB lock-on, Jump moved to F (Elden Ring style); gamepad RB, RT, B, R3; gamepad sprint moves to L3 | Space is the Souls dodge key |
| Dodge: stamina 25 once, 0.05 to 0.35 s i-frames, dash 900 cm/s, no animation yet (KI-007) | No roll in any pack |
| Combat: team ids (player 0, enemies 1), early inputs buffered 0.4 s, attacks need stamina above zero and may empty it | Souls-like rules |

## M4 boss and encounter (2026-10-18)

| Decision | Reason |
|---|---|
| Boss brain is `URPGBossCombatComponent`: weighted selection (distance, facing arc, phase, cooldown, repeat limit) with the random roll passed in | Distribution and rules are unit-tested |
| Boss attacks are `URPGBossAttackData` assets wrapping an `FRPGAttackData`; performing them reuses `URPGCombatComponent` (windows, hit trace, poise, death) | Same damage path as the player; no second combat system |
| Top-level boss flow (Dormant, Entrance, Combat, PhaseTransition, Dead) is owned by the C++ boss component and mirrored by a **StateTree asset** (`ST_Boss`, schema StateTree Component) | As originally locked. Thin mirror: custom condition `RPG Boss State Is` and task `RPG Boss Mirror`; each state has the task, every state transitions on tick to any state the component is in. The tree is built and compiled by `URPGBossStateTreeBuilder` (`Scripts/Editor/setup_m4_statetree.py`), so it is reproducible. StateTree and GameplayStateTree plugins enabled; modules StateTreeModule, GameplayStateTreeModule, AIModule, GameplayTasks added |
| Phase changes once per threshold: the first hit across it makes the boss untouchable, so same-frame hits cannot start a second transition | Test `Boss.PhaseAndFlow` |
| Boss is untouchable while Dormant, in Entrance and during PhaseTransition (`SetExternalInvulnerable`, independent of i-frames) | No cheese during roars |
| `URPGEncounterSubsystem` (world subsystem) runs start, victory, defeat, auto-retry after 4 s, and `VerifyResetInvariants` after every reset; `ARPGEncounterTrigger` starts it | Reset leaves no stale state: 10 cycles in `Boss.Encounter.ResetCycles` |
| Boss moves by direct steering (no navmesh), turns toward the player until the first hit window, then commits | Greybox arena; tracking cutoff is the fairness rule |
| `ARPGHUD` canvas HUD: player bars, boss bar, YOU DIED / ENEMY FELLED | No asset dependency; UMG in polish |
| Boss attacks use Sevarog montages in the `FullBody` slot; `AM_Sevarog_PhaseRoar` reuses `Ultimate_Targeting`, `Lightning` is a radial placeholder using `Cast` | No roar or lightning animation in the pack |

### How the pack is configured (found so far)

- A character is data: `BP_PlayerInfo` data assets hold default attributes, `ExtendedAttributes`, ability sets, combat style, state classes, input mapping contexts, UI widgets, cues and target types. `BP_BaseCombatCharacter` only stores the PlayerInfo reference. Enemies use `BP_EnemyInfo`.
- Attributes are gameplay-tag keyed (`Attribute.Health`, `Attribute.HitCount`, ...) and extended attributes are Blueprint classes (`BP_BaseRegeneratableAttribute` for Stamina, Health and Mana). Poise fits as one more regenerating extended attribute.
- Damage runs through `BP_DamageExecution` (185 nodes) and `GE_DamageBase`; hit reactions are `GA_BaseHitReaction` and `GA_HitStun`, which already counts hits (`Hit Count Attribute Tag`). A poise break can drive the same hit-stun ability.
- Python cannot read Blueprint variables; the plugin server (`Scripts/mcp_call.py`, editor open) can query and modify Blueprints, CDOs, levels and world settings.

`URPGBossStagger` (`Source/OneBossFight/Player/`, attached to `BP_ExampleGreatSwordBoss` by `URPGPlayerMovesSubsystem`, no pack edit) watches the boss's `GA_GS_Boss_HitStun`; when it becomes active (a poise break) it: ends that flinch ability, applies the pack's `GE_HitStunImmune` (4 s, covers the whole sequence) so later hits do not replay a flinch, holds the boss's behaviour (`BP_BehaviorManagerComponent` `StopBehaviorLogic`, as the Sevarog director did) and stops its movement, plays the pack knockdown clip `KnockdownStart_Anim_Montage` (1.92 s) and freezes it at 1.55 s so the boss stays down until `StaggerSeconds` (2.5) after the break, then plays `Knockdown_Getup_Anim_Montage` (1.4 s, first 1.03 s invulnerable in the clip), resumes the behaviour, removes the immunity, refills poise and starts a 5 s cooldown. While down, any health lost is multiplied by `CriticalMultiplier` (2.5): the extra is subtracted from the health attribute (the hit that causes the break does not count). All values are properties of the component.

Verified in PIE with real input (`pie_boss_stagger.py`, log `LogRPGStagger`): two heavy presses (57 HP each) break the poise; stance break lasts 3.66 s from the break to the end of the get-up (down for 2.5 s), the boss does not move (position fixed) or attack in that time; a light hit that costs 41 outside the window costs 102, a heavy 57 costs 143 (x2.5), health 385 to 139; poise 100 afterwards; the boss attacks again 2 to 3 s later (3 attacks in 6 s); a break 3.1 s and one 0.5 s after the end are ignored (cooldown), the next one after 8.4 s staggers again; second window: critical heavy 156 to 12. No Blueprint runtime errors.

Edge cases (`Scripts/Editor/pie_boss_stagger_edge.py`, modes `boss_dies`, `player_dies`, `boss_resets`, all PASS 2026-10-19): the boss dying during the stance break ends the component (log "died during the stance break", no resume, immunity removed, `Status.Dead` set, the pack's death flow destroys the boss, no errors); the player dying one second into the stance break (the pack respawns the player 4.0 s later, after the 3.66 s sequence has finished) leaves the sequence untouched, the boss resumes, and at the respawn the pack resets it (health 500, poise 100, no stuck hold or immunity; it does not walk back to its start position, it re-equips and fights where it stands); if the pack's reset ever lands while the boss is down, health rising during the stance break ends it at once (montages stopped, behaviour resumed, immunity removed, poise refilled), tested by setting the boss to 500 HP mid-stagger.

Limits: the look is fall and lie (the pack has no kneeling stance-break clip), not a kneel; the critical is a damage multiplier, not Elden Ring's riposte animation (the pack's execution, `GE_AllowFatality` with `GA_Player_FatalityAttack` and `GA_FatalityVictim`, needs paired clips and was not tried); any health loss while down is multiplied, whatever its source; the fall and get-up are untested by eye.

### Lock-on camera (2026-10-20, user hand test: "the camera goes to the ground too often")

Cause (measured with `Scripts/Editor/pie_camera_probe.py`, spring arm 370 cm, collision on, control rotation): the pack's `BP_TargetingComponent.UpdateTargetingControlRotation` aims the control rotation at `target actor location - (0,0,150)` with the pitch clamped to -25..+30, measured from the player's origin. The boss's origin is its capsule centre (149 cm up), so the aim point was the floor under it: lock-on pitch -17 to -25 degrees with the camera 264 to 309 cm up, most of the screen floor. Aiming at the chest was worse: pitch +23 swings the 3.7 m boom down and the camera sat 12 cm above the floor looking up. The fix (`Scripts/lockon_aim_height.py`, pack asset edited in place, original backed up outside the project): aim `target location - (0,0,40)` and clamp the pitch to -8..+12. Result at 250, 450 and 800 cm from the boss while locked on: camera height 130 to 154 cm, pitch +0.6 to +4.4 degrees, boss head 7 to 23 degrees above and feet 9 to 26 degrees below the screen centre (the view reaches 29 degrees), screenshot checked. Not changed: the free camera (pitch is the player's stick), spring arm length and lag. Not tested: smaller enemies, a boss right on top of the player, a controller stick during lock-on.

## Hit intake and the plan for Gate 3 (M7, 2026-10-21)

- The player's hits on the boss are read from the pack's own event dispatcher (`BP_CollisionComponent.OnHit(FHitResult)`), bound by reflection from C++ (`URPGHitIntake`): no pack asset is edited (owner rule), the binding refuses to attach when the signature is not one `FHitResult`, and `PackWiring` guards every name. The alternatives were polling the trace target's hit set (misses a clear and refill inside one frame) and watching the boss's health (cannot tell the attack).
- The attack data is read one frame after the event (see `MILESTONE_GATE3_CODE.md`); two hits in the same frame are marked shared because the pack's hit data then holds only the last.
- Gate 3 plan: a data table per (weapon, attack kind), a posture pool of our own with the pack's poise pinned full (the Freeze 17.1 asks to keep posture and poise apart; the pack's edited gate drains 20 or 50 per hit and cannot be given per-weapon numbers without editing it), stamina cost, hyperarmor window, bleed, builds. Rows M8 to M14 in `MILESTONE_GATE3_CODE.md`.

## Gate 3 code: posture owner, stamina, hyperarmor, bleed (M9 to M12, 2026-10-21)

- Posture is a pool of our own in `URPGBossPosture` (100, 6 s delay, 13 per s); the pack's poise attribute stays the boss's armour and is pinned full every 0.05 s (a poll, not a clamp). A pack hit stun that starts anyway (two heavy hits inside one pin interval take its 100 to 0) is ended and counted (`GetPackStunSuppressedCount`), never read as a break: the table's drains decide. A pool at zero asks `RequestBreak`; if the gate drops the request (a cooldown) the pool regenerates from zero after the delay instead of staying empty.
- The phase threshold waits while the player's `URPGHitIntake` has a pending record: the intake finishes a hit one frame after the pack's event, and without the wait a threshold crossing in the same frame could start the roar over a break that was earned (Freeze 1201).
- Stamina: the swing tracker sets the stamina attribute to what the row says instead of calling the pack's `Modify Attribute` (called from C++ with zeroed enum arguments it does not add). The pack's own 15 is paid first, the difference is taken or given back at the swing start (never below zero, never above the maximum).
- Hyperarmor: the pack's own `GE_HitStunImmune` on the player inside the row's window (montage seconds). The effect lasts 4 s and is not applied while active, so a longer window gets it applied again every 3 s; a failed apply is logged once per swing, not retried every frame. The player's `GA_PlayerHitStun` lists the tag in its ActivationBlockedTags (the ability can only start through the hit pipeline's event with source tags, so the test checks the data and the tag, not a hand-started stun). Damage is not touched: the damage resolver only looks at `Status.Invulnerable`.
- Bleed: `RPGBleedRules.h` holds the rules (order dead, dormant, transition, same frame), `URPGBossBleed` the component. A proc writes the health attribute directly, tells the stance break component that the loss is not a hit (`AcknowledgeHealthLoss`), leaves one point at least, and plays a blood effect and an impact sound loaded once in BeginPlay. The effect asset renders nothing in 5.5 until V-12 (KI-024).
- Packaging: assets loaded by `/Game` path are listed by directory in `Config/DefaultGame.ini` (`DirectoriesToAlwaysCook`), checked by the automation test `OneBossFight.Content.CookCoverage`; the alternative (a cook manifest asset with soft references) was not needed because the directories are few and stable.

## Boss death clip (G2-9, 2026-10-22)

- The pack kills the boss with `GA_EnemyRagdollDeath_C`: physics at once, the actor destroyed 4.35 s later, and its `DeathMontages` array is ignored (set by reflection in the probe, no effect). So the project plays the death clip itself (`URPGBossDeath`, OwnClip): on the first frame the boss's health is 0 (after it was seen alive) the clip `AN_Boss01_DeathLegend` plays through `RPGBossClips`, every tick the mesh is taken out of physics again (the pack's ragdoll switches it on in the same frame and the capsule moves it), the clip is paused at 3.0 s of its 3.5 s (the last second is the same pose).
- The death flow of the pack is never delayed or cancelled: the victory banner (the HUD polls the health), the kill slow motion and the destruction of the boss are untouched; the clip lives inside the 4.4 s the pack gives it. A death inside a stance break or a riposte (`ApplyCritical`, `EndRiposteExecution`) stops only its own montages and the component takes over.

## Review D and the builds loadout (M13, 2026-10-22)

- The boss look hides the pack's own sword (the static mesh component `Weapon Mesh`, a child of the pack mesh) and restores it on revert; the pack mesh keeps driving the pose and the weapon trace (KI-086, KI-088). A missing socket, piece or sword mesh is a logged warning, never silent.
- The death component ticks after the stagger, posture and phase components (tick prerequisites), so a death raised in their tick is seen in the same frame and the pack's ragdoll gets no free physics step. A critical hit that takes the last health activates `Ability.Dead` like the riposte impact. `ResetEncounter` is refused while the boss is dying (a dead boss stays dead: the pack destroys it about 4.4 s after its death whatever is done, KI-083); the refusal is counted.
- `rpg.Build` (Starter, Strength, Dex; empty = no choice) is a process wide console variable read by `URPGBuildLoadout` on the pack player. With no choice nothing is called in the pack and nothing is locked. The equip is the pack's own `Update Equip Slot Item` on the weapon item of the weapon slot, update type Update, while the boss sleeps; a choice made while the boss is awake is deferred. The enum bytes are read from the pack's enums (KI-089). The slot's weapon item is replaced, never the magic staff: when the staff is active the pack is asked to cycle back first (KI-091).
- The in-fight lock (Q2 of `M13_BUILDS_PLAN.md`) is the quickslot ability blocked on the ability system component, only while a build is chosen and the boss is awake (KI-090). The equipment slot's own disabled flags are never used. The HUD truth rule stands: the build line says what is really held.
- The hit intake takes the swing tracker's kind (Strong, Charged, JumpHeavy) when the pack's attack data says Default (the dual swords) and the montage is the swing's; two hits of one swing on the boss in one frame are one record for the table (posture, bleed). The pack's own damage is not changed (KI-092).

## Hyperarmor windows and the build line (M13/M14, 2026-10-22)

- The Strength build's hyperarmor is data in the weapon attack table (`DA_WeaponAttacks`, rows of `ClaymoreCombatStyle`): Strong and JumpHeavy 0.352 to 0.618 s (the pack plays one montage, `Ability_E_Anim_Montage`, for both; weapon trace 0.432 to 0.618), Charged 0.423 to 1.005 s (`ChargedAttack_Montage`, trace 0.503 to 1.005). Rule: the window opens 0.08 s before the first trace window and closes with the last (Freeze 5, 20.1: only the authored part of the downswing; the effect is the pack's own `GE_HitStunImmune`, HP damage still lands). The starter sword, the dual swords and the light swings have none. The asset is written by `set_weapon_windows.py` (idempotent, only these rows) and `FillDefaults` has the same numbers, so a fresh asset agrees; the automation test checks the defaults and the saved asset.
- The HUD build line is part of the boss HUD widget (top centre; the pack's own HUD owns top left, top right and bottom left), filled by `URPGBossHud` from the player's `URPGBuildLoadout` (`GetBuildLine()`): it shows only while a build is chosen, also while the boss sleeps, and says what the player really holds (the truth rule), with the suffixes of the loadout. The widget is removed with the boss after its death.
- M14 balance runs are a scripted player bot (`pie_build_fight.py`), not a replacement for the owner's feel test: three rows in `RunDrivers.ps1` (`-Only`), the checks are sanity only, the numbers are read by a human; the bot does not cheat (no heal, no hold, no teleport after the wake).
- M14 run identity is mandatory: the driver accepts exactly one scenario word, sets `rpg.Build` before PIE, moves the player outside the wake gate for reset, and verifies dormant 500 health / 100 posture plus the equipped build before the wake. Each result is archived with its source hash. The first valid runs are mechanics evidence only: Starter won in 25.7 s (one break/riposte), Strength in 37.7 s (three), and Dex died in 10.2 s after one bleed proc; Dex is inconclusive, so no combat value changes follow.
- Cold-spawn loadout readiness is the populated `EquipmentSlots` weapon slot, not `CurrentCombatStyle`: an unarmed `None` style must apply the chosen build once that slot exists. Requiring a non-None style creates a permanent wait because the equip is what restores the style; `pie_builds.py` 103/103 and 22 automation tests prove the fix.

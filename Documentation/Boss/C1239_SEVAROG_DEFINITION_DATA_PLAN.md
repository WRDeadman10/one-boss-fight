# C-1239: Sevarog `URPGBossDefinition` data plan

**Status:** design plan only. No definition asset, animation asset, annotation, runtime configuration, source code, or Content was changed. This is a proposed mapping of the A-720 move list to the existing typed data shape; it is not approval to create the asset or proof that the moves can run data-only.

## Scope and source rules

The plan uses `Documentation/Boss/C1239_SEVAROG_ANIMATION_INVENTORY.md` and its Section 7 move list, with engine-read facts traced there to `Docs/BossCombatReview/Execution/Claude/P_C1239_SEVAROGPROBE/probe_sevarog.log`. The exact runtime authoring shape is `URPGBossDefinition` in `Source/OneBossFight/Player/RPGEncounterBinding.h` and `FRPGAttackTiming` / `FRPGAttackTrackerConfig` in `Source/OneBossFight/Player/RPGAttackTracker.h`.

The move list's “Estimated Timing” ranges and its narrated combat roles are design hypotheses, not probe measurements. They are deliberately excluded as values for `CommitTime`, `ActiveStartTime`, `ActiveEndTime`, `RecoveryEndTime`, damage, reach, cooldown, phase threshold, or any other runtime field. Sequence duration and `root_motion=False` are the only per-sequence animation facts used below; montage root motion is `n/a` in the probe. `root_motion=False` does not establish whether the animation's root bone translates; root-bone displacement has not yet been measured. No timing window can be inferred from clip length.

Owner constraint from C-1239: use Sevarog's own animations and do not retarget. C-1240 reports that probe v2 resolved both `Swing1_Medium_Montage` and `Swing2_Medium_Montage` notifies as `NamedNotify SaveAttack` and `ResetCombo` (the Paragon combo-chain markers). This resolves their identities, not their timestamps, combat windows, or suitability as the final authored contract. Do not repurpose or mutate the pack montages.

## Existing shared code to reuse before adding anything

### Selection, combo, and card start

- `FRPGBossMoveSelector::Select` evaluates each compiled card against the move model, tracks refusals/cooldowns, scores eligible cards, and returns a chosen index and `MoveId` (`Source/OneBossFight/Player/RPGBossMoveSelector.cpp:33-83`). The generic character builds candidates from its profile and calls the selector (`Source/OneBossFight/Boss/RPGFrameworkBossCharacter.cpp:75-78,460-461`); after the decision it calls `StartCard` with the corresponding compiled profile card (`RPGFrameworkBossCharacter.cpp:521-526`). This is the existing data-driven Sevarog-card selection route; do not add a second selector.
- The card schema has `MoveId`, a source `Sequence` or `Montage`, slot, authored timeline, hit windows, damage, and bounded warp fields (`Source/OneBossFight/Player/RPGBossMoveCard.h:70-101`). The current framework playback contract is sequence-only: validation rejects a card with a non-null `Montage` or null `Sequence` (`Source/OneBossFight/Boss/RPGFrameworkMoveExecutor.cpp:62-67`). `StartCard` then calls `PlaySlotAnimationAsDynamicMontage` on the selected card's `Sequence` (`RPGFrameworkMoveExecutor.cpp:122-160`). It does not activate a Blueprint ability; it creates and plays the dynamic montage directly. Therefore Sevarog move cards should point to Sevarog sequences and use card-owned timing/window data. If a requirement depends on preserving a source montage's authored notifies or section semantics, prove that separate playback need; the Paragon `SaveAttack`/`ResetCombo` markers are not required by the shared combo graph.
- Combo continuation is data-driven: the character starts a combo when the selected `MoveId` matches the graph root (`RPGFrameworkBossCharacter.cpp:568-576`), steps the graph using card outcome and a fresh target snapshot, looks up the next graph node's card by `MoveId`, then starts that card through the same executor (`RPGFrameworkBossCharacter.cpp:767-816`). A1→A2 should therefore be represented as Sevarog card IDs plus combo-graph data, subject to reviewed outcome/range branches; no new combo orchestrator is justified by the inventory alone.
- Scope boundary: this selector/executor path belongs to `ARPGFrameworkBossCharacter` + `URPGBossFrameworkProfile`. `URPGSevarogDirector` is a separate pack-specific gate/phase/lightning component and does not call the card selector. The current `URPGBossDefinition::AttackTracker` is not itself the framework profile. The plan identifies the companion profile/card route explicitly; it does not claim a live Sevarog registration has already been proven.

### Stun and intro

- The generic profile exposes `StaggerStartAnim`, `StaggerLoopAnim`, and `StaggerEndAnim` (`Source/OneBossFight/Player/RPGBossFrameworkProfile.h:132-141`). Its compiler requires a coherent trio and validates the sequence set (`RPGBossFrameworkProfile.cpp:76-81,275-296`). On posture break, `ARPGFrameworkBossCharacter` starts the first sequence (`RPGFrameworkBossCharacter.cpp:702-719`), then `TickStaggerAnim` plays the loop and end clips through the same sequence-to-dynamic-montage slot path (`RPGFrameworkBossCharacter.cpp:823-856`). The listed Sevarog Stun sequences are representable as profile data and do not need a new state driver; they still need skeleton/slot/profile validation and a confirmed Sevarog route.
- `URPGSevarogDirector` already gates/holds pack behavior and, when the gate opens, activates a configured `EntranceAbility`; it holds behavior for `EntranceHoldSeconds` before resuming (`Source/OneBossFight/Boss/RPGSevarogDirector.h:62-71`, `RPGSevarogDirector.cpp:315-345`). The director also directly plays its configured phase-two roar montage (`RPGSevarogDirector.cpp:170-192`). These are existing ability/montage start routes. Its entrance field is an ability class, not an arbitrary `LevelStart_Montage` field, so verify which ability is assigned and which project-owned clip it plays before calling the intro data-ready.
- The director's wider Sevarog-specific scope is already implemented: player-distance gate (`RPGSevarogDirector.h:32-38`, `.cpp:526-533`); phase-two health threshold and walk-speed scale (`.h:36-46`, `.cpp:170-192,560-566`); optional aura/material presentation (`.h:48-56`, `.cpp:195-241`); optional parry-recoil montage (`.h:58-62`, `.cpp:244-252`); and a phase-two ranged-lightning ability with range/idle scheduling (`.h:72-76`, `.cpp:460-489,571-590`). These routes do not establish that Sevarog's proposed definition/cards are bound to the selected encounter actor, nor that its configured entrance ability plays the project-owned `LevelStart_Montage`.
- The card path is not an ability activation path: selected card data starts its sequence as a dynamic montage (`RPGFrameworkMoveExecutor.cpp:122-160`); a unique gameplay ability such as life drain or lightning still needs an ability/effect route, while ordinary animated moves should remain data on shared cards. Do not classify the lack of montage-card support as lack of montage start: the shared executor generates the montage from a sequence. A requirement to start an arbitrary existing montage object from a card is unsupported by the current validator/player (`RPGFrameworkMoveExecutor.cpp:62-67,122-160`) and would justify only that narrow adapter if genuinely needed.

## Remaining verified gaps / conditional work

Use the shared selector, card player, combo graph, stagger driver, and director routes above. Add code only where a selected Sevarog card's required contract is outside those capabilities or the real Sevarog actor cannot use the existing profile route. A generic subsystem's presence does not prove this specific boss is registered to it. Never edit pack assets in `/Game/ParagonSevarog/`.

1. **A4 dash/lunge and A3 slam step-in:** `FRPGBossMoveCardSpec` already has bounded post-commit target-closing warp with a per-card distance/angle budget and optional smoothstep (`Source/OneBossFight/Player/RPGBossMoveCard.h:94-101`); `URPGFrameworkMoveExecutor::TickWarp` moves the actor with collision (`Source/OneBossFight/Boss/RPGFrameworkMoveExecutor.cpp:423-478`). Check whether its timing contract (after commit and within active end) fits each required displacement. The root-bone translation probe remains open. Only if this route cannot satisfy the measured path is further work needed: (a) enable root motion on duplicated project-owned copies only if the probe proves root translation exists, or (b) extend the shared data-driven displacement module for the unsupported trajectory. Do not assume root translation or change `/Game/ParagonSevarog/`.
2. **A5 Subjugation:** card windows can carry direct/secondary/ring hit shapes, but the inventory does not prove a target-positioned rupture, snare, or interruption/cancel contract. First check whether the ground effect fits existing card windows and a verified effect route; add a mechanic module only for unsupported targeting/snare/state behavior.
3. **A6 ultimate:** profile phase cards can gate eligibility and move-card hit windows can describe coverage, but the plan has no approved 360-degree trace geometry or radial knockback contract. Verify a data-card representation against Sevarog's skeleton/contact source; add code only for any missing coverage/effect behavior.
4. **A7 Soul Siphon:** no current definition field/card effect has been shown to implement channel target selection, health transfer, and interruption rules. Verify an existing ability first; otherwise this unique life-drain behavior needs an add-on ability/module and native tests.
5. **Sevarog route binding:** inventory whether the selected encounter actor can load a `URPGBossFrameworkProfile` containing Sevarog-owned cards and stagger clips, and whether the director's `EntranceAbility` plays the Sevarog-owned LevelStart clip. If these are separate fixture/director paths with no data route into the selected Sevarog actor, minimal integration to bind that data is a real gap. Do not add duplicate selector, combo, stagger driver, phase gate, or director behavior.
6. **Presentation and contact validation:** verify Sevarog skeleton/slot/sockets, actual hit windows, and chosen look/death/wake/transition references. Typed fields and card windows exist, so missing measurements or asset references are authoring/evidence gates; add a typed adapter only if verified behavior cannot be expressed by them. No reflection-only or unproven path substitution.

## Remaining checklist sequence and acceptance

1. C-1240's guarded probe has resolved the swing montage markers as `SaveAttack` and `ResetCombo`. Obtain and validate the exact Sevarog skeleton, mesh, sequence/card, montage, and socket paths for the companion profile.
2. Review each move's gameplay contract and choose which rows can use an existing verified ability vs. which require the code add-ons above. Approve source-backed stats, policies, phases, and presentation inputs.
3. Author Sevarog-owned attack montages/annotations with an idempotent authoring script that refuses conflicting assets/notifies, preserves unrelated notifies, reloads, reads back, and passes the strict audit. No retargeting.
4. Produce the final definition asset and complete `Fields` provenance; run definition preflight/native binding validation and validate all animation skeleton dependencies.
5. Only after strict audit, set source-backed `bUseMontageNotifyTimings=true`; Lead runs fresh-log off/on PIE timing parity on the data route using the hitch-aware driver. Keep the run ID, build ID, map/route, and raw log.
6. Lead reviews and accepts that evidence. Until then the Sevarog definition pipeline and move behaviors remain planned, not proven.

## Validator and playback constraints

- A card must have schema/IDs, exactly one sequence or montage, matching resolved animation/skeleton/mesh identity, a present slot, finite timeline/range/damage values, and `Commit <= ActiveStart < ActiveEnd <= RecoveryEnd <= resolved clip length` (`RPGBossMoveCard.cpp:34-59,88-92`). The exact skeleton, slot, IDs, play rate, and resolved metadata are not established by the contact sheets, so these remain TBD.
- A non-defensive card needs at least one window and at least one direct window. A defensive card instead must have no windows and zero damage; it also needs a readable 0.25 s real-time telegraph (`RPGBossMoveCard.cpp:93-100,156-161`, `RPGBossDefenseRules.h:8-22`). The defensive classification comment describes a backstep, but the validator does not require `bWarpAway=true` for every defensive card.
- A bounded warp turns on only with a positive distance or angle budget. Its interval must satisfy `Commit <= WarpStart < WarpEnd <= ActiveEnd`; distance and angle caps are 1000 cm and 180 degrees (`RPGBossMoveCard.cpp:60-68`). For defensive cards, the telegraph start uses `WarpStartSeconds` when a warp budget is enabled. The proposed Speedburst interval is therefore structurally representable if commit/rate/budget and profile fairness checks are later satisfied. The Swing3 step-in satisfies the source's inclusive start and strict end inequalities: `0.467 <= 0.467 < 0.533 <= 0.667`.
- `TickWarp` explicitly moves away only when `bWarpAway` is true; with false it sets direction toward the target and closes to standoff (`RPGFrameworkMoveExecutor.cpp:440-442`). Therefore a no-window, no-damage defensive Speedburst can warp forward without a validator or code change. This reuses the defensive flag for a reposition/setup action, although the header/rules' prose calls defensive cards backsteps. For actual profile resolution, defensive cards need `CooldownSeconds >= 3` (`RPGBossDefenseRules.h:16-22`, `RPGFrameworkProfile.cpp:237-242`). When `PunishMarginSeconds > 0`, the profile also checks counterplay after the move; forward warp adds zero backstep distance to that check (`RPGFrameworkProfile.cpp:261-268`). These fairness rules may still refuse candidate values.
- The existing combo graph can chain card MoveIds (`RPGFrameworkProfile.h:28-33,143-146`); after a no-hit Speedburst the executor's outcome is Whiff, and the character steps the graph from a fresh target snapshot (`RPGFrameworkBossCharacter.cpp:769-775,785-805`). A Speedburst root node with a Whiff edge to a `Swing1_FAST_v2` node is a possible data-only sequence, subject to including both cards, attack-count budget, and range/yaw branch constraints. No live Sevarog profile or these graph values were verified.
- Runtime playback requires resolved assets, a non-null `Sequence`, null `Montage`, no montage section, and the damage/defensive rule; the executor generates a dynamic montage from that sequence (`RPGFrameworkMoveExecutor.cpp:62-67,152-160`). These draft rows do not prove that a live Sevarog actor is bound to the framework profile.

No code, assets, runtime values, tests, Unreal, PIE, build, commit, or push were changed/run for this draft or source audit.

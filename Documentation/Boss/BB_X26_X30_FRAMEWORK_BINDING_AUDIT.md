# Queue BB Batch 6: X26–X30 Framework binding audit

**Scope:** Sevarog signature-card add-on readiness, test-only encounter selection, autonomous selector driver, HUD health binding, and framework-boss death completion. Static source/doc review only; no Unreal, build, card/map save, or asset write was performed in this batch.

## Disposition

| Task | Status | Finding / acceptance |
|---|---|---|
| X26 S7/S8 card rows | **BLOCKED: effect values are unsourced** | C-1242 gives S7 release pose at 0.800–0.867 s and S8 channel pose at 0.267–1.267 s (`C1242_SEVAROG_CONTACT_MARKING.md:22,31`). The draft table supplies provisional base-card candidates, but no source selects S7 target-ground radius/delay/snare or S8 tick cadence/heal fraction/cone. C-1274 reports explicitly leave these to Lead/owner. A validator-only transient row with invented effect values would not prove an authored card, so no such values were fabricated. Resume when the add-on configuration is sourced; then run the transient C++ validator dry-run under both locks. |
| X27 test-only data-route selection | **BLOCKED: selection is not framework-boss binding** | `rpg.EncounterDefinition` is development-only and empty by default (`RPGEncounterSelectionSubsystem.cpp:18–23`). It selects a `URPGBossEncounterDefinition`, but `BuildWorldBindingInternal` insists on exactly one `IsPackBoss` pawn plus one pack player (`:161–195`). The Sevarog proof actor/profile is currently reached through the separate `SpawnFrameworkBossForTest` bridge (`RPGFrameworkBossCharacter.cpp:66–76`); the existing CVar therefore cannot select and run that framework actor as the encounter boss. Do not label the existing generic CVar as Sevarog data-route acceptance. |
| X28 selector-driven fight driver | **BLOCKED: available bridge forces cards** | `InitializeWithProfileForTest` sets `bTestInitialized` through `InitializeProofInternal` (`RPGFrameworkBossCharacter.cpp:66–73,111`). Automatic selector entry is gated by `!bTestInitialized` (`:491`), while `StartCardForTest` and `StartComboForTest` directly choose IDs (`:161–212`). The current `pie_sevarog_framework_live.py` uses those forced methods. A truthful selector-driven run needs a distinct dev-only autonomous test-init path; this batch does not add an unverified C++ hook. |
| X29 framework-boss HUD | **BUG: no native-health binding** | `RPGPlayerMovesSubsystem` creates `URPGBossHud` only for `IsPackBoss(Pawn)` (`:888–892`). The HUD reads its owner exclusively with `RPGPack::ReadAttribute(Attribute.Health)` and derives victory from that result (`RPGBossHud.cpp:415–422`); it does not query `IRPGNativeBossHealth`. `ARPGFrameworkBossCharacter` implements that interface (`RPGFrameworkBossCharacter.h:17,71–73`) and stores its health natively. Failing scenario: an initialized framework Sevarog reaches zero native HP while the HUD is bound to the pack boss/its attribute; the bar/victory latch has no framework-health witness. No fix was made pending the X27 actor/UI ownership design. |
| X30 framework death → encounter end | **BUG: death has no encounter/HUD completion signal** | Framework damage calls `Die()` at `RPGFrameworkBossCharacter.cpp:771–777`. `Die()` stops movement, aborts its executor, and logs `boss_dead`/`RESULT` (`:1008–1018`), but does not broadcast a completion delegate, update `URPGBossEncounter`, or notify `URPGBossHud`. In contrast, the HUD's victory path is driven by the pack `Attribute.Health` read (`RPGBossHud.cpp:417–422`). Failing scenario: player damage kills the framework actor; its local result log appears, but the surrounding pack encounter remains active and no framework-bound victory/retry flow is entered. No integration change was made in this audit. |

## Evidence and next seam

The two confirmed integration defects (X29–X30) share an ownership gap: the data-route activation/HUD system is pack-boss based, while the Sevarog framework actor currently exists on a proof/test bridge. Before adding another test CVar or HUD, provide a single framework encounter owner/binding seam that owns health, victory, retry/reset, and teardown. X26 remains a values gate; X28 remains an autonomous-init gate.

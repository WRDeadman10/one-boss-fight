# X-2047 / A-850 hotfix: v2 receipt proposal, artifact hash typing and backup state consistency

Assigned by X-2047 (lead Codex) to C (implementer), 2026-11-12, from Antigravity's findings AG-R39 and AG-R40 (A-850). **SOURCE CHANGED:** `Scripts/Tools/sevarog_receipt_v2_proposal.py` only. That is a disconnected proposal module; it has no runtime or asset behavior and nothing executes it.

The BK-131..135 report (`BK_131_135_RECEIPT_V2_SCHEMA_PROPOSAL.md`) is unchanged. **Proposal only; X-1991 is still open.**

## Fixes

1. **Artifact hash typing.**
   - **Bug:** `_key()` built comparison keys with `str(...)`, so JSON `null` and the string `"None"` compared equal. A receipt carrying `sha256: "None"` could therefore validate where the derived artifact expects `null`.
   - **Fix:** every artifact must now pass `_artifact_typed()`: `kind` is one of `lock`, `backup`, `asset_needs_operator`; `path` is a string; and `sha256` is **JSON `null`** (the permitted unknown state) or **64 lowercase hex**. `_key()` no longer coerces anything, and it encodes `null` as its own sort slot.
2. **Backup state consistency.**
   - **Bug:** `copy_result: "created"`, `cleanup_attempted: false`, `cleanup_readback: "absent"` was accepted as `final_state: kept_evidence`. That reports a copy as kept when it was observed absent and nobody tried to remove it.
   - **Fix:** this combination is now refused with "a created backup observed absent without a cleanup attempt is inconsistent".
   - **Still valid:** an absent readback after a **failed** copy (`final_state: none`), and a created copy removed after a cleanup attempt (`removed`).

## Limits

- `final_state` is still derived from executor observations. The validator checks that they are consistent with each other, not that they are true.
- An `unknown` copy result with an absent readback and no cleanup stays `unknown`, as before. A-850 named only the `created` case.

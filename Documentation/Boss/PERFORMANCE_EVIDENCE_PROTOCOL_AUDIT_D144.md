# D144 — performance evidence protocol audit

Date: 2026-11-03  
Scope: reconcile the owner performance target with benchmark capture, runbook, and percentile implementation. Static documentation/source audit; no benchmark run.

## Target and capture protocol

| Requirement | Current protocol | Assessment |
|---|---|---|
| Product gate | Packaged game, 1920×1080, full boss encounter including phase 2; average FPS >=60 and frame-time p99 <=16.67 ms. 120 FPS / 8.33 ms is stretch only (`PERFORMANCE_LOG.md:3`; `RPGFrameStats.h:9`). | Explicit. Both average FPS and p99 must pass; neither can substitute for the other. |
| Scene and encounter | `RunBenchmark.ps1` defaults to `/Game/OneBossFight/Levels/L_SevarogArena`, windowed 1920×1080, forced resolution, fight mode, and packaged executable (`Scripts/RunBenchmark.ps1:14-18,28-36`). The runbook requires `fight_started=true` and drops a capture that measured an idle arena (`GATE4_RUNBOOK.md:9,41`). Fight mode keeps the bot active, raises the boss to full health before 30 seconds, then forces phase two at 30 seconds and heals the boss to keep the encounter running (`RPGBenchmarkRunner.h:63-79`; `.cpp:198-260`). | Explicit positive encounter coverage. A separate value records `fight_started`; phase two is intentionally forced to make it part of the timed scene. |
| Warm-up and timed interval | Runner defaults to 5.0 seconds discarded warm-up and 60.0 seconds recorded (`RPGBenchmarkRunner.h:41-45`). The runbook repeats 5-second discard / following 60-second interval and asks for one disposable warm-up plus three identical retained baseline runs (`GATE4_RUNBOOK.md:35-41`). | Explicit. The first sample is added on the first Tick whose elapsed time reaches the warm-up boundary, using the time since the preceding Tick (`RPGBenchmarkRunner.cpp:153-167`); this can include the final frame interval that straddles the cutoff. |
| Sample count | Each run writes `frames.csv`; `summary.json` records `frames` (the valid sample count) and duration. The runbook says retain all three pairs and the raw files (`GATE4_RUNBOOK.md:41,49-51`). Historical packaged baselines record per-run counts, e.g. 2,191 (`PERFORMANCE_LOG.md:20`). | Actual count is observable and retained, but there is no minimum accepted frame count. Duration is fixed, sample count varies with measured frame rate/hitches. Reviewers should report each run's actual `frames`; do not infer a count from duration or the preallocated capacity. |
| Hardware/session | Each summary records GPU/driver, CPU, RAM, OS, engine version, build config and resolution (`RPGBenchmarkRunner.cpp:360-390`). The runbook requires the physical console session, intended NVIDIA GPU, valid `fight_started`, hardware/session/VSync metadata and consistent driver/build across comparisons (`GATE4_RUNBOOK.md:3-5,9,51`). | Percentile math | `FRPGFrameStats::Compute` removes non-finite/non-positive samples, sorts the frame times and uses nearest-rank (`ceil(P/100 × N)`, one-based) for p50/p95/p99 (`RPGFrameStats.cpp:7-21`). | Repeatability | The runbook requires three baseline captures with the same driver, hardware, map, launch mode and CVar string and retains each raw result pair (`GATE4_RUNBOOK.md:41-51`). | Three repeats are specified; there is no numerical spread/variance acceptance rule. Report all three instead of selecting only a favorable run. |

## Protocol gaps and cautions

- There is a fixed 60-second capture duration and a recorded actual frame count, but no explicit lower bound on sample count. At a throttled or very slow run, p99 is calculated over fewer samples; the protocol does not define when that sample set is too small for acceptance.
- The first included sample's wall interval can begin just before `WarmupSeconds`, because the guard tests current elapsed time while `Delta` is `Now - LastTickTime`. This is at most one frame interval around the boundary; the log does not expose a separate effective start timestamp for the sample window.
- The 30-second phase-two transition is forced by the benchmark harness to ensure that phase two appears in the measured window; it is not evidence that a natural full fight reached phase two at the measured gameplay time.
- Three repeats and the p99 math are stated, but no combined statistic or run-to-run tolerance is defined. Preserve and assess each run separately against the target and record variation without inventing an average-of-p99 rule.

The capture protocol specifies warm-up, scene, hardware, retained sample count, and percentile method. The open items above are interpretation limits, not reasons to omit these fields from a report. No performance measurements were created or changed in this audit.

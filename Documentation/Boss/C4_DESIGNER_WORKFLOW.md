## 1. Boss prerequisites

Before preparing a boss config, confirm the authored Skeletal Mesh and Animation Blueprint match; the AnimGraph has the required `FullBody` slot; the attack animations are in-place; and each referenced move card has valid sockets, timeline, ranges, and skeleton. The mesh and animation assets are authored prerequisites, not generated by `new_boss.py`. Use the exact checklist and field constraints in C1 §1–2.

## 2. Safe boss creation

1. Copy a C1 example config to a new config file. Choose a unique `boss_name`, package destination, card `MoveId`, and any authored `WindowId`; update both the config and its referenced card spec.
2. Run `new_boss.py <config.json> --dry-run` through `run_editor_script.ps1` with a new absolute `-OutDir` and `-Task`. Resolve every validator error before any apply run.
3. Confirm the preflight reports absent destinations and review the exact output package list. Do not reuse the checked-in example destinations.
4. Run the create command only for the unique config. The utility writes new card/profile/proof-map assets and reads back authored profile properties. If a destination collision or partial failure occurs, stop and preserve assets; follow C1 recovery guidance and ask the asset owner/Lead to reconcile references.
5. Review the run log and content snapshot. A successful content-creation run is not a PIE witness; use the Lead-owned F4 proof process for runtime acceptance.

The utility's exact command, schema, and failure tokens are in C1 §§2–3. `-OutDir` must be absolute. Example assets can already exist in the project and will be refused.

## 3. Weapon prerequisites and catalog workflow

Before C3, have the pack-authored combat-style DataAsset, item DataAsset, item base class, weapon actor class, and melee ability class ready. The ability's montage chain, notify timing, item attachment, and hit-trace setup require Editor/DCC authoring; the C3 JSON does not create them.

For a new weapon, copy the C3 example config and give it unique `weapon_id`, unused `style_name`, build ID, console name/aliases, and distinct new definition package paths. Fill all six supported attack rows and provide a catalog icon under a cooked root. `catalog.register` is a JSON boolean. New catalog builds use `legacy_slot: -1`; never change a legacy compatibility slot.

Run C3 `new_weapon.py <config.json>` first without `--apply`. Inspect the validator result and the catalog collision/root preflight. Only then run with `--apply` and a fresh output directory. The utility edits `DA_WeaponAttacks` and `DA_CombatCatalog` and creates two new definition assets; it refuses existing destinations and live identity/token collisions. It reads back written fields and root references. Preserve those references if a run stops partway.

An Editor readback is not native catalog acceptance. The catalog compiles at game-instance startup, so runtime acceptance requires the Lead's fresh Editor/game-instance startup and PIE proof. `CATALOG_COMPILE_PENDING` marks this boundary. See C3 §§2–5 for full schema, commands, evidence, and recovery.

## 4. Validate Boss walkthrough

In the Content Browser, select exactly one boss AnimBlueprint or one `RPGBossFrameworkProfile`. Run the single-command dispatcher from the Editor Python console:

```python
exec(open('C:/UnrealProject/OneBossFight/Docs/BossCombatReview/Execution/Codex/C2/run_validate_boss.py', encoding='utf-8').read())
```

For an AnimBlueprint, the selected asset is compiled without saving and the receipt reports status/generated class plus best-effort compiler log lines. For a profile, the action reads and validates the selected fields through the C1 offline validator mirror; it does not compile, save, or call the native framework validator. Both routes emit structured receipts. Zero/multiple selection and unsupported asset classes are refused with diagnostics. See C2 for direct actions and the exact acceptance boundary.

## 5. Safety and completion checklist

- Use unique new destinations; never use overwrite as a recovery mechanism.
- Review the dry-run and selected package list before an apply run.
- Keep prerequisite assets and existing references intact; do not delete/recreate assets that may be referenced.
- Keep raw run logs, before/after prerequisite hashes, and changed-package lists with the run receipt.
- Separate static/profile preflight, Editor save/readback, native startup compilation, and PIE evidence in acceptance reports.

This guide connects the three tools. It does not grant runtime, build, or production-content acceptance; the detailed evidence requirements remain in C1/C2/C3 and the Lead's run receipt.

## 6. Compile and preflight errors

Use the failure layer to choose the next check:

- `Selection.Count`, `Selection.WrongAssetType`, and `Selection.Stale` are C2 selection/dispatch problems. Correct the Content Browser selection and rerun.
- `BlueprintCompile.*` diagnostics refer to AnimBlueprint compile status, generated class, or captured compiler lines. Open the asset's Compiler Results for full context; the Python compile API returns no detailed result object.
- `Profile.*` or `Framework.Profile.*` means the reflected profile snapshot failed the offline C1 rules. Follow the field token back to the C1 profile schema. The profile action is not a native `ResolveProfile` call.
- `Weapon.Config.*` indicates an input/catalog issue; the error table in C3 maps each token to the JSON field. A destination or live catalog name collision requires a new unique identity/path, not overwriting the existing asset.

If Editor compile status and profile preflight both pass, native catalog/profile resolution still needs the appropriate fresh startup and proof run. Keep those results separate.

## 7. Framework proof-map workflow

Use a new, uniquely named framework proof package directory per boss fixture. C1 creates the profile and `L_<boss>FrameworkProof` map, plus the required floor/player-start/fixture/nav setup. Confirm the profile and proof map destinations are absent before applying. The map must use the framework proof game mode and point at the intended profile; C1's setup script reads authored fields back before saving. Follow C1 §3 for the actual creation command and C1 §4 for the runtime proof.

Proof maps establish framework behavior in an isolated fixture. They do not prove the pack boss's own Blueprint hit-reaction response; that needs a separately scoped integration proof.

## 8. F4 command and evidence capture

The required F4 driver parameters are `-Map`, `-OutDir`, and `-Task`. Use the generated proof map and a new absolute output directory for every run. Add only the driver flags required by the specific proof, such as `-RealBuild` or `-InjectRow`; the C1/C3 guides define their meanings.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Docs\BossCombatReview\Execution\Claude\F4\run_pie.ps1 `
  -Map "/Game/OneBossFight/FrameworkProof/<unique-map-name>" `
  -OutDir "C:\UnrealProject\OneBossFight\Docs\BossCombatReview\Execution\Claude\F4\runs\<unique-run-name>" `
  -Task "F4_<unique-task-name>"
```

Preserve the raw Editor log, driver summary, command/config, and before/after content state with the run. Record exact distances, selected asset/card, refusal tokens, exit status, and any ERROR lines. Do not call a result witnessed from a summary token alone if the required observable needs raw log or image evidence.

## 9. Token troubleshooting

| Token family | First place to look | Action |
|---|---|---|
| `Framework.BossConfig.*` | C1 config and destination preflight | Correct the schema or choose new unique names and paths. |
| `Framework.Profile.*` | C1 profile validator and profile field guide | Correct the named domain/reference field; keep partial optional blocks all-or-nothing. |
| `MoveCard.*` | C1 card spec and mesh/animation prerequisites | Correct skeleton, socket, timeline, range, or clip data before authoring. |
| `[C2_VALIDATE]` / `[C2_PROFILE_VALIDATE]` | C2 structured receipt | Use `action`, `asset_path`, `field`, and diagnostic `code`; compiler log attribution may be best-effort. |
| `[Weapon.Config.*]` | C3 field table and troubleshooting table | Correct the indicated config path and rerun the no-write preflight first. |
| `Catalog.*` / `Weapons.*` / `Builds.*` | Native startup catalog log | Verify references and legacy invariants; restart the game instance after catalog edits. |

## 10. Unique naming and no-overwrite rules

Give every new boss, move/card, weapon, build, map, config, task ID, and run output directory a unique name. Re-running the same config is expected to refuse existing destinations. For C3, also avoid catalog `WeaponId`, `BuildId`, style alias, console name, and build alias collisions. Never overwrite or delete an existing referenced package as a way to make a run pass. Preserve partial outputs and ask the asset owner/Lead to resolve the reference state before any recovery operation.

## 12. Novice dry-run review

Read this guide as a first-time designer: the order is prerequisites → copy config and assign unique IDs → no-write validation → review planned destinations → apply → fresh runtime proof. The distinction between `new_boss.py --dry-run` and `new_weapon.py` without `--apply` is called out; the checked-in sample configs can collide with existing assets and should not be applied unchanged. The Validate Boss step tells the designer to select exactly one supported asset before using the dispatcher. No step suggests deleting a referenced package to clear an error.

# How to add an opt-in framework profile field

Use this eight-step path for a setting that is disabled by default and must be validated, observable, and safe across resets. `GuardChipFraction` and `ParryRecoveryScale` are the current examples. A profile field does not need a console variable; add one only when a proof or test needs a runtime control.

1. **Declare it in the profile header.** Add a reflected `UPROPERTY(EditAnywhere)` field to `URPGBossFrameworkProfile` with an explicit disabled default and a comment stating units/semantics. Examples: `GuardChipFraction=0.f` and `ParryRecoveryScale=0.f` in `RPGBossFrameworkProfile.h:95–97`. Zero means off in both cases.
2. **Validate it and name the failure token.** In `RPGBossFrameworkProfile.cpp`, reject non-finite/out-of-domain values and any disallowed profile scope. Return a stable `Framework.Profile.<Field>` token so callers and tests can identify the failure. The existing checks are at `:133–136`; runtime tests assert these tokens at `RPGFrameworkRuntimeTests.cpp:168–184`.
3. **Register the proof-log schema.** If the feature emits a `[FrameworkProof]` token, add its payload regex to `SCHEMAS` in `validate_framework_proof_logs.py`. Current examples are `guard_chip` and `parry_recovery` at `:201–202`. Keep payload names and numeric/string types aligned with the actual `UE_LOG` format.
4. **Add tests for profile validation and wiring.** Cover default-off, valid endpoints, non-finite and out-of-range values, profile-scope restrictions, and the stable error token. Add a pure rule/wiring boundary test when the setting changes runtime behavior; the profile tests are `RPGFrameworkRuntimeTests.cpp:157–184`, and the parry wiring case is `RPGBossParryRecoveryWiringTests.cpp:7–8`.
5. **Document the setting and proof.** Update `TASKS.md` and `TEST_PLAN.md`; add a field reference or feature-specific `*_EXPECTED.md` with units/defaults, exact enable/control setup, expected relation, source citations, and limits. Existing examples are `GUARD_CHIP_EXPECTED.md` and `PARRY_RECOVERY_EXPECTED.md` in the Codex proof folder. Do not claim a live pass until a log has been captured and validated.
6. **Emit and index a useful log token.** Emit only on the meaningful feature branch, and include the values needed to evaluate the expected relation. Guard chip logs `incoming` and final `applied` damage at `RPGFrameworkMoveExecutor.cpp:291,413`; parry recovery logs `grade` and `extra` at `RPGFrameworkBossCharacter.cpp:593`. Add the payload row to `Documentation/Boss/LOG_TOKENS.md` and its regex to the validator schema (step 3).
7. **Audit every state reset and exit path.** Trace where runtime state is created/armed and where it is consumed. Check `Rearm`, `Die`, `Fail`, interruption/abort, and object teardown (`EndPlay`) as applicable. Stateless `GuardChipFraction` needs no runtime-state reset. Parry recovery's pending duration/grade/deadline are cleared on initialization/Rearm/Die/Fail (`RPGFrameworkBossCharacter.cpp:78,861,878,887`); verify any new state at all analogous paths.
8. **Update `TEST_HOOKS.md` only for a new test control.** If adding a CVar or test hook, document its exact name, default, units/accepted values, behavior, and disable value in `Documentation/Boss/TEST_HOOKS.md`; keep test-only registrations out of Shipping. The existing player-guard proof control is listed at `TEST_HOOKS.md:11`. A profile field alone does not belong in that CVar table.

Source examples: [`RPGBossFrameworkProfile.h`](../../Source/OneBossFight/Player/RPGBossFrameworkProfile.h:95), [`RPGBossFrameworkProfile.cpp`](../../Source/OneBossFight/Player/RPGBossFrameworkProfile.cpp:133), [`GUARD_CHIP_EXPECTED.md`](../../Docs/BossCombatReview/Execution/Codex/Proofs/GUARD_CHIP_EXPECTED.md), and [`PARRY_RECOVERY_EXPECTED.md`](../../Docs/BossCombatReview/Execution/Codex/Proofs/PARRY_RECOVERY_EXPECTED.md).

To print these eight sites for a new member without editing files, run `python -I Scripts/Tools/new_profile_field_scaffold.py --field MyField --error-token Framework.Profile.MyField --log-token my_field`. Add `--test-control` only when the change introduces a CVar or test hook. The output is a checklist; follow the actual feature owner and lifecycle paths before editing.

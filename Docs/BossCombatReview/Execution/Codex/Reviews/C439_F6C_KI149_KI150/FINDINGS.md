## Findings

1. **[P2] A rejected restart mutates target health before validating the boss restart state.** `Source/OneBossFight/Boss/RPGFrameworkProofFixture.cpp:89-90` calls `SetTargetHealth` before `OwnedBoss->RestartEncounter`. The latter rejects an active/nonterminal boss or a stale generation at `Boss/RPGFrameworkBossCharacter.cpp:162`; by then maximum/current HP have already been written and read back by fixture lines19-20. Concrete scenario: generation1 is still attacking, target health/ExpectedTargetHP are765 after an accepted35HP hit; call `RestartEncounterForTest(2)` before death/completion. It sets target current HP back to800, then returns false with `Framework.Boss.RestartState` because the boss is active. The still-running encounter now sees800 versus ExpectedTargetHP765 and fails at character lines84-88 on its next tick. A positive but stale generation request also refills HP before returning false. Thus rejection is not side-effect-free, and an erroneous/duplicate driver request can manufacture the health mismatch the fixture is meant to diagnose. A later failure within the write/readback chain similarly has no explicit cleanup/rollback in the restart wrapper. Validate restart eligibility/generation before either write; define the fail-closed handling for any failure after mutation. Add an invalid/active/stale restart control that checks both health values and existing encounter state stay unchanged on refusal. The successful C438 max-first ordering itself is correct; this finding concerns preconditions/failure paths, not a claim KI-150's old clamp persists.

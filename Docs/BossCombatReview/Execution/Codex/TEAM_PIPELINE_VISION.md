# One Boss Fight — complete team pipeline and product vision

Owner request: a long, coherent pipeline for BOTH Claude and Antigravity. Current authority: Codex technical lead/independent critic; Claude implementation and sole engine operator; AG assigned content/offline/tooling and only later exact approved-batch git operator. This roadmap is a standing queue and acceptance contract. It does not blanket-release future Source edits, engine jobs, asset writes, activation or git.

## Product vision

Ship a readable, fair, responsive boss duel AND a reusable combat foundation. The owner should create a player build, a compatible weapon and a genuinely distinct boss using project-owned Data Assets/Details, then validate them and fight without a bespoke C++ edit for each instance. The pack remains a supported backend; original pack assets stay untouched. A custom wizard follows proven native authoring, not the other way around.

The second boss must demonstrate materially different authored moves/phases and the Boss01–canary–Boss01 replay, with stable targets, resets and generation-safe events. Multiplayer/server authority is required, not an optional waiver. Final output includes a stable packaged build, reproducible proof, clear authoring instructions and a reviewable repository history. Target packaged1080p60FPS/p99<=16.67ms on the accepted hardware/proxy policy;120FPS stretch only. A5 visual work remains parked unless owner explicitly changes that constraint; required gameplay is not waived.

## How the two lanes work

- Claude lane C: runtime C++, actual tests, serialized editor/build/automation/cook/package and real asset application when specifically released.
- Antigravity lane A: actual staged authoring tools, typed content inputs, project-owned source animation/presentation/audio deliverables when scoped, offline regression/review artifacts and final reviewed git batches. No engine takeover implied by content work. Claude runs AG tools in the editor until a different explicit handoff is issued.
- Codex lane X: own independent contract/probe code, source/calling-path review, raw-log/hash verification, ownership/authority decisions and next exact work orders. No engine/process/bridge operations or git writes.

Every stage has a concrete product and observable exit gate. Actual code/assets are reviewed before execution; focused tests precede appropriate full-suite tests. Synthetic checks never substitute for real UE/asset/gameplay/network/package proof. Source acceptance is not execution acceptance. No repeated prose proposal or unchanged baseline rerun in place of implementation. A source delivery can be split into independently reviewable chunks while nondependent work continues.

## Evidence and review rhythm

1. Claim exact files; record actual baseline/full source/asset/config pins appropriate to the packet. Preserve concurrent work.
2. Implement real bounded behavior and meaningful tests; deliver diff/Review/pins and limits. Failed attempts stay immutable.
3. Codex reviews actual source/content/calling path. Errors yield exact code corrections, not a blanket redesign loop.
4. Release one serialized Claude execution order with frozen inputs. Stop at first failure/drift, preserve first failing source/logs; exact reviewed delta before retry. No blind compiler-fix rounds or expected-list weakening.
5. Verify actual job exits, discovered test identities/unique membership, raw warning/error/fatal/ensure diagnostics and SHA256/binary identity. A full pass on an old binary is not inherited.
6. Accept only the demonstrated scope and update work-card status/requirement evidence. Open limitations stay visible. Codex then releases the next ready card(s).

Engine/Content writers never overlap. AG source/tools and Claude C++ work can proceed in parallel when claims do not overlap. While the editor/build gate owns frozen inputs, other agents work on new offline artifacts, not the frozen tree. Git batches wait for stable accepted pins and exact include/exclude/path plan; AG alone executes the released batch. No history rewriting.

Socket messages are the coordination record; no scheduled polling. Listener delivery needs model-turn handling and rearming; do not advertise a background connection as autonomous model wakeup. Owner questions are answered promptly. Notify meaningful decisions/deliveries/failures, not routine acknowledgments.

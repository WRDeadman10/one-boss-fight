# KI-153: player parry grant path

- **Player builds and styles.** `rpg.Build` accepts Starter, Strength, and Dex in [RPGBuildLoadout.cpp:561](../../../../Source/OneBossFight/Player/RPGBuildLoadout.cpp:561); [RPGBuildRules.h:51-53](../../../../Source/OneBossFight/Player/RPGBuildRules.h:51) maps them to `SwordCombatStyle`, `ClaymoreCombatStyle`, and `DualSwordCombatStyle`. [RPGCombatCatalog.cpp:84-95](../../../../Source/OneBossFight/Player/RPGCombatCatalog.cpp:84) builds the style asset paths and aliases: Starter can also use `SwordAndShieldCombatStyle`, Dex can also use `TwinbladeCombatStyle`. Polearm is explicitly off-build, not a selectable `rpg.Build` entry ([RPGBuildRules.h:75](../../../../Source/OneBossFight/Player/RPGBuildRules.h:75)); its asset is `.../Weapons/Polearms/PolearmCombatStyle`.
- **Grant property and current coverage.** Each style's `AbilitiesSet` is `Array<Struct(F_AbilitySet)>`; the struct row holds `InputTags` (GameplayTagContainer) and an `Abilities` array of ability classes ([PR5_SwordCombatStyle.txt:11](../Claude/Evidence/exports/PR5_SwordCombatStyle.txt:11); row text at [inspect_run1/editor_raw.log:1252](../Claude/B_PARRY/inspect_run1/editor_raw.log:1252)). Existing editor scripts read/write `get_editor_property('AbilitiesSet')` ([grant_parry.py:18-34](../Claude/B_PARRY/grant_parry.py:18)); the practical mapping is `InputTag.Parry` -> `GA_PlayerParry_C`. The live grant attempt read back successful additions for Sword and Claymore, but skipped DualSword and Polearm because neither had the expected single `InputTag.Block` -> `GA_PlayerGuardBlock_C` row ([grant_run1/editor_raw.log:1248-1276](../Claude/B_PARRY/grant_run1/editor_raw.log:1248)). `SwordAndShieldCombatStyle` was inspected and has a block row, but is not in that grant script's `STYLES` list ([inspect_styles.py:4-8](../Claude/B_PARRY/inspect_styles.py:4), [grant_parry.py:4](../Claude/B_PARRY/grant_parry.py:4)). Thus the current grant evidence covers standard Starter sword and Strength claymore; it does not establish parry on the Starter shield alias, Dex aliases, or polearm.
- **Input and timing.** `BP_CombatPlayerCharacter.uasset` contains the `IA_Parry` input event and `InputTag.Parry`; `IMC_AdvancedControls.uasset` references `IA_Parry`. The ability class is `GA_PlayerParry_C` (`.../Abilities/Player/GA_PlayerParry.uasset`); its class tag is `Ability.Parry`, and its graph routes `GameplayEvent.Parry` to `Try Activate Abilities By Tag` for `Ability.Parried` ([PR2_GA_PlayerParry.t3d:1196-1205, 2048-2050](../Claude/Evidence/exports/PR2_GA_PlayerParry.t3d:1196)). The `ParryMontages` variable is an array of `F_AbilityMontage`, consumed by `Get Ability Montage` ([PR2_GA_PlayerParry.t3d:1989-2011, 2442](../Claude/Evidence/exports/PR2_GA_PlayerParry.t3d:1989)); the inspected CDO has no populated parry-montage entries ([PR2_CDO_GA_PlayerParry.t3d:1-26](../Claude/Evidence/exports/PR2_CDO_GA_PlayerParry.t3d:1)). `ParryFramesNS` adds `Status.ParryActive` on notify begin and removes it on notify end ([PR2_ParryFramesNS.t3d:151-160, 356-364](../Claude/Evidence/exports/PR2_ParryFramesNS.t3d:151)). The active window is the notify-state duration authored in a montage; the inspected notify/CDO exports do not provide a numeric duration, and no populated montage was found to measure.
- **Hit response.** Pack `SM_BlockStanceEnemyImpactDecision` checks `Status.Blocking` ([PR2_SM_BlockStanceEnemyImpactDecision.t3d:152](../Claude/Evidence/exports/PR2_SM_BlockStanceEnemyImpactDecision.t3d:152)); its inspected graph does not check `Status.ParryActive`. `GA_PlayerParry` routes the `GameplayEvent.Parry` event to activate the `Ability.Parried` response by tag ([PR2_GA_PlayerParry.t3d:1196-1205](../Claude/Evidence/exports/PR2_GA_PlayerParry.t3d:1196)). In the project's framework proof, the sampled perfect-parry run logged `combo_gate ... outcome=Parried` and completed ([pie_parry3_perfect/editor_raw.log:2331-2334](../Claude/B_PARRY/pie_parry3_perfect/editor_raw.log:2331)); the framework classifies the player's `Status.ParryActive` tag in [RPGFrameworkBossCharacter.cpp:269](../../../../Source/OneBossFight/Boss/RPGFrameworkBossCharacter.cpp:269).
- **Risks and open integration.** The owner has chosen to include player parry. Close the style-coverage gaps before calling it available on every weapon: add/verify entries for `SwordAndShieldCombatStyle`, `DualSwordCombatStyle`, and `TwinbladeCombatStyle`; decide whether off-build polearm needs it. Add and verify compatible parry montage data containing `ParryFramesNS`, otherwise the ability can be granted without an authored animation/window. The mechanic can reward precise timing with a distinct parried response and change the duel's damage, follow-up, and duration balance; run representative Starter/Strength/Dex fights after the style and montage coverage is complete.

Static analysis and review of existing logs/scripts only. I did not edit pack assets, run Unreal, build, or run PIE.

## Algorithm (`RPGBossHydrationPreparation.cpp`)

1. Game thread only: `IsInGameThread()` is the first statement; off the game thread the call returns `Preparation.NotGameThread` before any UObject or input weak pointer is read.
2. `CompilePreflight` over the ENTIRE input; any rejection returns the preflight's own named errors, no artifact, no component. The plan is retained (world, encounter, slots, targets, the very config and content leases, class leases, five plans per boss-core member). A plan/request alignment check (`Preparation.PlanMismatch`) guards the participant order; the explicit selected phase id of each request is recorded.
3. Allocate, for every boss-core member in request order and the five plans in plan order (Stagger, Phases, Encounter, DormantWake, Posture): `CheckMember` (world valid, encounter valid, role boss-core, weak actor valid and not being destroyed, same world, not begun or beginning), refuse if another consumer of the class or another live object (or an object of another class) already carries the instance name under the actor, `NewObject<UActorComponent>(Actor, Class, Name)` leased in the same statement that stores it, then `CheckComponent` (valid, not being destroyed, exact class, exact instance name, `GetOwner()` and the actor's owned set, not registered, not begun) and `CheckMember` again. All ten (for two bosses) components exist and are unregistered before the first configure; a target-only member gets none.
4. Configure, same order: `CheckMember` and `CheckComponent` before, the accepted plan callback with the member's validated config (its diagnostic carried unchanged in `Preparation.ConfigureRejected`), `CheckComponent` and `CheckMember` immediately after. The old `CreateConfigureRegister` is never called, no target is looked up or inferred, no player0, no context or subsystem is touched, nothing is loaded, registered, begun or ticked.
5. After each real allocation and each real configure the dev-only counter may inject a failure (the steps are counted from 1: allocations 1 to 10, configures 11 to 20 for two boss-core members).
6. On any failure the same `Abort()` used for the artifact destroys everything created for EVERY member (earlier participants too) before the result returns, and the cleanup report's errors are appended; no artifact is returned. Success sets `bPrepared` and returns the artifact.

## Abort and destruction

`Abort()` is refused off the game thread without touching anything; idempotent (`bAborted`); iterates members and owned components in reverse; per owned component: a missing, garbage or being-destroyed component, or a stale/garbage owner (weak, never dereferenced), counts `AlreadyGone` and is released; a component that is registered, begun or no longer owned by its actor is a contract violation (reported with slot and name, left in place, no rollback pretended, not destroyed); anything else gets exactly one `DestroyComponent()`. All leases are then released. The destructor does the same on the game thread (and logs only when the cleanup was not clean); off the game thread it is a flagged contract violation (`ensureMsgf`) that touches no UObject and cleans nothing.

## Lifetime assumptions (stated, not proven by the tests)

The caller keeps and releases the artifact on the game thread, keeps the actors spawned and unchanged while it lives, does not mutate the input during the call, and holds no other reference to a destroyed component. The engine replaces a same-name garbage object in place when the name is created again before collection (read in `UObjectGlobals.cpp`, `StaticAllocateObject`); the preparation refuses any LIVE other object with an instance name and accepts only an earlier garbage object of exactly the planned class, and no test keeps a reference across a reuse (a stale weak pointer would otherwise alias the new object). `bAutoRegister` is left at the native default, so an engine path registering all components of the owner would register these; the artifact cannot prevent that and Abort reports it.
